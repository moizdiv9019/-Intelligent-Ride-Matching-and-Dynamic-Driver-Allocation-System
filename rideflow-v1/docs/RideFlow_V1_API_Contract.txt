RideFlow V1 API Contract
========================
Version: 1.0.0
Base URL: /api/v1

1. PROJECT TECHNOLOGY
----------------------
- Frontend: React + Vite + JavaScript
- Backend: FastAPI + Python
- Database: Supabase PostgreSQL + PostGIS
- Authentication: Supabase Auth + Google OAuth
- Realtime: Supabase Realtime
- Maps: Leaflet + OpenStreetMap
- Routing: OSRM-compatible routing provider

2. GENERAL API RULES
---------------------
- Content type: application/json
- Authentication header: Bearer <Supabase access token>
- Timestamp format: ISO 8601 UTC
- Coordinates: lat = Latitude (-90 to 90); lng = Longitude (-180 to 180)
- Distance: metres
- Duration: seconds
- Fare: Decimal string, for example 750.00
- Default currency: INR
- Success response format:
{
  "data": "Endpoint-specific response object"
}
- Error response format:
{
  "error": {
    "code": "MACHINE_READABLE_CODE",
    "message": "Human-readable message",
    "details": {},
    "request_id": "string"
  }
}

3. AUTHENTICATION
------------------
- Supabase Auth handles signup, login and Google OAuth; these are not FastAPI endpoints.
- FastAPI verifies Supabase JWT signature, issuer and expiry.
- Never trust a user_id supplied by the frontend as identity.
- Keep service-role keys and database credentials on the backend only.

5. COMMON ERROR CODES
----------------------
- HTTP 400 | VALIDATION_ERROR: Invalid request fields
- HTTP 401 | UNAUTHORIZED: Missing or invalid token
- HTTP 403 | FORBIDDEN: User lacks permission
- HTTP 404 | NOT_FOUND: Resource not found
- HTTP 409 | RIDE_STATE_CONFLICT: Invalid state transition or concurrent update
- HTTP 409 | OFFER_EXPIRED: Driver offer expired
- HTTP 409 | DRIVER_UNAVAILABLE: Driver is no longer eligible
- HTTP 429 | RATE_LIMITED: Too many requests
- HTTP 502 | ROUTING_ERROR: Routing provider failed
- HTTP 503 | SERVICE_UNAVAILABLE: Required service unavailable

Standard error response structure:
{
  "error": {
    "code": "MACHINE_READABLE_CODE",
    "message": "Human-readable message",
    "details": {},
    "request_id": "string"
  }
}

6. SEQUENTIAL DRIVER ALLOCATION
--------------------------------
1. Find eligible drivers using verification, availability, fresh GPS and vehicle suitability.
2. Use PostGIS to shortlist nearby drivers, then road ETA to rank them.
3. Send an offer to one driver at a time.
4. Initial offer expiry: 15-20 seconds, configurable.
5. On rejection or timeout, mark the offer and create the next offer.
6. Never offer the same ride to the same driver twice.
7. If all candidates are exhausted, set ride status to no_driver_found.
8. Use a worker with database locking or atomic conditional updates to process expired offers once.

7. SUPABASE REALTIME COMMUNICATION
----------------------------------
Transport: Supabase Realtime Postgres Changes
Tables used for Realtime:
- rides
- ride_offers
- ride_events
- driver_locations
Subscriptions:
- Driver | Table: ride_offers | Purpose: Receive their own new ride offer
- Passenger | Table: rides | Purpose: Receive ride status and assignment changes
- Passenger on active ride | Table: driver_locations | Purpose: Receive assigned driver's permitted live location
Security: Enable RLS and restrict subscriptions to authorised records. Realtime notifies the UI; FastAPI remains authoritative for business operations.

9. GPS, MAPS AND ROUTING
------------------------
- Map display: Leaflet with OpenStreetMap tiles.
- Routing: OSRM-compatible routing provider; use road distance and road ETA to rank drivers and estimate journeys.
- GPS updates: Driver browser sends latitude, longitude, accuracy, heading, speed and recorded timestamp to the backend.
- Store/update the driver's latest location; do not create a new location row for every GPS ping.
- Use PostGIS to shortlist nearby drivers and routing ETA to rank the shortlist.
- Expose approximate driver locations to unrelated passengers. Exact assigned-driver location is only for authorised active rides.
- Browser GPS may not continue reliably when the mobile browser is in the background or the phone is locked. Keep the driver app in the foreground for the V1 demo.

10. IMPORTANT IMPLEMENTATION NOTES
-----------------------------------
- POST /rides uses client_request_id as an idempotency key; add a unique constraint on passenger_id and client_request_id.
- Accept an offer in a database transaction: update offer, ride assignment, driver availability and ride event atomically.
- Add rejection_reason to ride_offers if storing rejection reason outside event metadata.
- Driver cancellation before journey starts releases the driver and restarts dispatch; an in-progress ride must not be silently reassigned.
- Nearby-driver results should expose approximate locations only to unrelated passengers.
- Browser GPS is not guaranteed while mobile browser is backgrounded or device is locked.
- Backend calculates estimated and final fares; never trust fare values submitted by frontend.
- All example UUIDs, coordinates, addresses, fares and timestamps are illustrative.

11. RIDE STATUS FLOW
--------------------
requested -> accepted -> arriving -> ongoing -> completed
Other possible outcomes: cancelled, no_driver_found
A driver cancellation may restart dispatch only before the journey starts. Never silently reassign an in-progress ride.
